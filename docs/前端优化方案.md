# 前端修改优化方案

> 归档说明（2026-11-23）：桌面端已移出主项目并冻结留存，本文涉及桌面端的章节仅作历史记录，不再适用。网页端部分照旧有效。

> 审查日期：2026-11-23。本轮仅审查，未改代码。
> 依据真实截图 + 前后端代码审查，确认的调整方向（grill-me 结论）：
> 1. 聊天面板 = 可展开的紧凑框（默认紧凑弹幕发送框，点开展开成含历史的完整面板）
> 2. 两端风格各自保留（网页端浅色暖灰、桌面端深色直播），聊天面板用 CSS 变量各配各的
> 3. 昵称改用自定义输入框，不用 `prompt()`

---

## 一、逻辑漏洞 / Bug

### 1. `prompt()` 不支持（严重）
- **位置**：`public/app.js:59-67` `ensureNickname()`
- **现象**：实测控制台报 `prompt() is not supported`，点「开始共享/加入」直接失败，无法进入任何共享流程。
- **原因**：`prompt()` 在自动化浏览器、Tauri WebView、部分移动端浏览器被禁用。
- **方案**：删掉 `prompt()`，改用页面内自定义昵称输入框（见「昵称输入」小节）。

### 2. 聊天面板/弹幕退出后不清理（内存泄漏）
- **位置**：`public/viewer.js:53-54`、`public/host.js:81-82` 创建 `ChatManager`，但 `viewer.leave()`/`_end()`、`host.stop()` 都没调 `chat.destroy()`。
- **现象**：停止共享/退出后，`#chat-panel`、`#danmaku` 残留，事件监听不清理。
- **方案**：在 `viewer.leave()`、`viewer._end()`、`host.stop()` 里补 `this.chat?.destroy()`。

### 3. 聊天消息列表无限累积（内存泄漏）
- **位置**：`public/chat.js:97-104` `_appendChat()` 只 append，无上限。
- **方案**：消息列表超过 100 条时删除最早的（`list.firstChild.remove()`）。

### 4. 弹幕轨道随机重叠
- **位置**：`public/chat.js:93` `el.style.top = (6 + Math.random() * 58) + '%'`
- **现象**：弹幕随机落位，会互相覆盖，可读性差。
- **方案**：改成固定轨道轮换（如 5 条轨道，按序号取模分配 `top`）。

### 5. rtc 首帧检测定时器 close 后不清理
- **位置**：`public/rtc.js:113-138` `_watchFirstFrame()` 的 `setTimeout(check, 200)` 与 12 秒超时定时器未在 `close()` 清理。
- **现象**：连接关闭后定时器仍跑约 12 秒。
- **方案**：`close()` 里清理 `_watchFirstFrame` 的定时器（保存引用）。

### 6. 观众页浮层按钮超标（违背设计）
- **位置**：`public/index.html:113-120` 浮层有 6 个控件（录制/时间/静音/详情/全屏/退出）。
- **现象**：产品设计要求「观众页浮层仅 3 个按钮」。
- **方案**：浮层只留「全屏/静音/退出」3 个；录制、详情收进「详情」面板或「更多」。

## 二、聊天面板重构（可展开的紧凑框）

**目标形态**（截图参考）：
- **默认紧凑态**：右上角小浮层，只有标题「弹幕」+ 白色输入框 + 紫色发送按钮，无消息列表。消息只走画面弹幕。
- **展开态**：点标题或展开按钮，浮层展开成含历史消息列表的完整聊天面板。

**结构**（`public/chat.js` 与桌面端 `desktop/ui/index.html` 共用同一套 DOM 语义）：
```
[弹幕 | ◉弹幕开关 | 展开/收起]
（展开时出现）消息列表
[ 输入框        | 发送 ]
```

**配色**：全部走 CSS 变量 `--chat-bg / --chat-head-bg / --chat-input-bg / --chat-accent / --chat-text`，两端各自定义（见下一节）。

**交互**：
- 默认紧凑（`collapsed` 类），点「展开」切到完整态。
- 弹幕开关、面板展开状态各自独立。
- 历史消息只在展开态渲染；紧凑态不 append（避免 DOM 堆积）。

## 三、视觉风格（各端各自保留）

**结论**：网页端保留浅色暖灰（产品设计基调），桌面端保留深色直播（原生应用惯例）。聊天面板作为「浮在画面上」的 HUD，两端都用「视频黑 + 一档提亮」的深底，避免与各端浅色外壳冲突，同时保持两端聊天面板观感一致。

| 变量 | 网页端（app.css） | 桌面端（index.html） |
| --- | --- | --- |
| `--chat-bg` | `#1A1A1E`（视频黑提亮） | `#1F1F23` |
| `--chat-head-bg` | `#232327` | `#26262C` |
| `--chat-input-bg` | `#FFFFFF`（亮块焦点） | `#FFFFFF` |
| `--chat-accent` | `#7C3AED` | `#9147FF` |

**理由**：聊天面板的本质是「画面上的 HUD」，它的参照系是黑视频区而非页面外壳。用「视频黑的一档提亮」做底 + 一个白输入框制造焦点 + 单一紫色强调，比「贴一块浅色面板在黑画面上」更不割裂。

## 四、昵称输入（自定义输入框）

- **位置**：`public/app.js` 的 `ensureNickname()` 重写；桌面端 `index.html` 的 `startShare()` 前加同一逻辑。
- **方案**：首次使用（`localStorage` 无 `share-nick`）时，弹一个页面内自定义输入框（复用 `ui.js` 的 `blocking()` 或独立轻量 modal），确认后写 `localStorage`，之后不再问。
- **理由**：`prompt()` 兼容性差、样式丑、与产品极简风格冲突；自定义输入框可控样式、可校验、可给默认值。

## 五、桌面端 UI 调整

基于截图，需调整：

1. **补主操作**：未共享态画布中央应是醒目的「开始共享」主按钮（紫色圆形），下方才是说明文字；「高级设置」降为次级链接。
2. **按钮语义**：未共享时隐藏/禁用「停止共享」「复制邀请链接」；共享后启用。
3. **窗口尺寸**：默认加大（如 1000×680），让预览区不显空。
4. **标题栏**：保留最小化/最大化/关闭（截图里只有 ✕ 是旧版/未生效，需确认）。
5. **底部控制条**：主按钮「开始共享」用紫色填充；「复制链接」「网页版」为次按钮。
6. **房间号占位**：未共享时隐藏「房间 ---」，共享后再显示。
7. **对比度**：次要文字从 `#7C7C85` 提亮到 `#ADADB8` 以上。

## 六、为什么这么调整（总结）

1. **修 bug 优先于美化**：`prompt` 崩溃、内存泄漏是硬伤，先堵住。
2. **聊天面板「可展开紧凑框」**：默认不占画面（符合「展开不挤压、收起正常」的诉求），展开能看历史（保留「一个消息系统两种展示」）。
3. **各端各配色**：强行统一反而破坏两端各自已成立的设计基调；用 CSS 变量让聊天面板两端观感一致、配色各配。
4. **桌面端补主操作 + 主次层级**：截图最大问题是「用户第一眼不知道该干嘛」，主按钮缺位是转化断裂的根因。
